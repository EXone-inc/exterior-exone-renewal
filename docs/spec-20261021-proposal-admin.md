- 作成日: 2026-10-21

- 合意した内容: 旧 `works` を「施工事例（旧テーマ）」と明示し、移行済みの新用事例 12 件を「提案事例」として登録・変更・削除できるようにする。デザインテイストも専用画面から管理する。
- 維持条件: PHP 7.4.33、旧テーマ・旧データ・CPTUI 設定・旧分類・コラム・フォーム・お知らせを維持する。テーマの切替は行わない。

## 1. 背景・目的

通常のローカルでは `works` が「提案事例」として編集できる。一方、本番共存用の `exr_works` と `exr_works_package` は公開保存領域から隔離され、編集画面がない。新テーマ側で提案事例を運用できるようにし、管理画面で旧テーマの施工事例との違いを明確にする。

今回の「提案事例」は現在の `/works/` と各詳細 URL へ表示する内容である。将来の実施工を扱う「施工事例（新テーマ）」の投稿型・画面・データは作らない。

## 2. 対象と境界

- 共存有効の新テーマでは「提案事例」を管理画面の独立メニューにし、その配下にデザインテイスト管理を設ける。管理者だけが利用できる。
- 同じ管理画面に存在する旧 `works` は表示上「施工事例（旧テーマ）」とする。表示名だけの変更で、旧テーマのソース、CPTUI の保存設定、旧投稿型・分類の構造は変更しない。旧テーマへ戻すと新テーマの処理はなくなる。
- 通常ローカルでは既存の「提案事例」編集と `works_package` のデザインテイスト管理を使用する。共存用の別一覧や「施工事例（旧テーマ）」を追加しない。既存の編集項目・名称・単一テイスト選択との整合を保つ。
- 現在のローカル用 `works` メタボックス・保存処理は、共存時に旧 `works` へ適用しない。共存時に旧投稿へ新用の 4 画像枠や新用テイスト保存を混入させない。
- 予約公開、URL 編集、階層の追加、英名編集、並べ替え機能、一括操作、事例の恒久削除、他のコンテンツ編集は追加しない。

## 3. F-01: 提案事例を管理する

### 3.1 事例の一覧・編集

一覧でタイトル、公開状態、テイスト、画像の有無、TOP 掲載の有無を確認し、新規登録・編集・ゴミ箱移動・復元を行う。既存の新テーマ用コンテンツ確認画面も「提案事例」と表示し、編集画面へ案内する。

入力は以下に限定する。

| 入力 | 挙動 |
| --- | --- |
| タイトル | 必須。既存詳細の和文見出しに使用 |
| 説明 | 任意。改行を保持するプレーンテキスト。HTML・ショートコードとして解釈しない |
| メイン画像／外観写真／3D パース／図面 | 各 1 枚、任意。標準メディアから権限のある画像を選択・解除 |
| デザインテイスト | 所有が確認できる専用テイストから 1 つ、または未設定 |
| TOP 掲載 | チェック式。新規の初期値は掲載しない |
| 公開状態 | 公開／下書き。新規の初期値は下書き |

既存の公開日時と URL 名は編集で変えない。新規は作成時の日時と一意の URL 名を自動で与える。画像の解除は事例との関連だけを外し、添付投稿・実ファイル・画像タイトル等は変更しない。現在の画像の表示順と未設定時の表示仕様を維持する。

事例の削除はゴミ箱移動とし、内容・ID・URL を保持する。復元で元の公開／下書き状態へ戻す。公開済みだった事例の復元は新テーマ側の掲載再開を意味する。ゴミ箱の間も URL を予約する。

### 3.2 デザインテイストの管理

専用画面で一覧・追加・名称変更・削除を行う。入力項目は名称だけとし、既存 6 テイストの ID・slug・取り込み識別を名称変更で作り直さない。名称の重複・空欄を拒否する。新規テイストの識別と slug は一意に自動生成する。

既存 6 名の英名対応と並びは現在の表示仕様を維持する。名称を変更した場合や新規の名称は、既存仕様どおり登録名を表示の代替値として使う。英名や独自の順番を編集する機能は追加しない。絞り込み候補は件数 0 のテイストも含む。

テイストを削除する前に利用事例数と「事例は残り、テイストが未設定になる」ことを表示する。削除は対象の専用分類と専用事例との関連だけを外し、事例・公開状態・画像・URL は保持する。削除した名称は選択肢と公開側の絞り込みから消える。

旧分類と共有された term ID、所属不明の事例との関連、想定外の子テイストがある場合は、他データへ影響しないよう名称変更・削除を停止する。別の分類への自動付け替えや子分類の移動はしない。

### 3.3 受け入れ基準

- [x] AC-01: 共存有効の新テーマでは「提案事例」と「施工事例（旧テーマ）」が区別され、移行済み 12 件は提案事例の一覧・編集から操作できる。新しい実施工用メニューは存在しない。通常ローカルでは既存の提案事例管理を継続できる。
- [x] AC-02: タイトル・説明・4 画像・単一テイスト・TOP 掲載・公開／下書きを登録・変更し、開き直して確認できる。不正な画像・別分類の ID・複数テイスト・配列などの不正入力は保存しない。画像解除でメディア実体は残る。
- [ ] AC-03: 公開事例は `/works/`、既存の詳細 URL、詳細内の一覧、テイスト絞り込みに反映される。TOP は公開かつ掲載チェックありの事例を既存仕様どおり新しい順に最大 5 件表示する。支店モードのリンク引き継ぎも維持する。
- [x] AC-04: 下書き・ゴミ箱は新用の一覧・詳細・TOP・検索から表示されない。旧テーマ・標準 REST・RSS へ新用事例や専用分類が混入しない。サイトマップには既存の公開条件を満たす事例だけが出る。
- [x] AC-05: 既存事例の ID・URL・元の取り込み識別／ハッシュは編集前後で同じ。新規は独自の UUID 識別を持ち、二重送信で増殖しない。ゴミ箱と復元でも ID・URL は変わらず、他事例の URL と衝突しない。
- [x] AC-06: 専用テイストの既存 6 件を表示し、追加・名称変更が事例の選択肢と公開側の絞り込みへ反映される。既存テイストの名称変更で term ID・slug・所属・取り込み由来が変わらない。
- [x] AC-07: 未使用と使用中の専用テイストを削除できる。使用中なら当該テイストの関連だけが外れ、事例本体・公開状態・画像・他分類の関連は保持される。古い編集画面から削除済みテイストを保存しようとしても復活・付け直しされない。
- [x] AC-08: 旧 taxonomy、共有 term ID、別データ集合、取り込み途中、重複識別、不明な投稿への関連を指定しても変更できない。削除対象の関係に異常がある場合は部分削除をしない。
- [x] AC-09: 管理者以外、共存無効、旧テーマ、nonce 不正、GET での変更要求は新専用処理を実行できない。操作ごとに対象所有を確認し、日本語の安全なエラーを示す。内部識別子や秘密情報を管理画面・ログへ出さない。
- [x] AC-10: 同じ事例／テイストの古い画面からの更新、事例への割当てとテイスト削除の競合を検出する。保存失敗で本文・メタ・分類関連の一部だけが確定しない。結果不明の確定エラーでは自動再送・誤った巻戻しを行わず確認を促す。
- [x] AC-11: 共存時に旧 `works` 編集画面へ新用メタボックス・保存・専用画像操作が混入しない。旧記事・旧分類・CPTUI options・フォーム・コラム・お知らせとその設定は対象操作前後で不変。通常ローカルの従来編集は引き続き動作する。
- [ ] AC-12: PHP 7.4.33 の構文と対象動作、管理画面 375px／1920px での登録・画像選択・削除確認を検証する。公開面は代表事例・TOP・一覧に絞って回帰確認する。本番配布は確定した新テーマファイルのみ、バックアップ・DB 初期投入・自動移行・テーマ切替を伴わない。

## 4. 保存・所有の契約

| 要素 | 契約 |
| --- | --- |
| 共存事例 | `exr_works` / `exr_stored`、所属 `_exr_dataset=exterior-exone-renewal:v1`、完了状態、許可する一意の source key が揃うものだけ |
| 公開状態 | `_exr_source_status` を事例の現在の公開／下書き／ゴミ箱状態として管理。保存状態を通常の publish / draft / trash に変更しない |
| 新規事例 | `exterior-exone-renewal:v1:admin:works:<UUID>` という別の識別。取り込み元 ID や由来ハッシュを捏造しない。URL 名は自動生成・変更不可 |
| 事例メタ | 既存の `_exterior_exone_works_image_main` / `_exterior_exone_works_image_exterior` / `_exterior_exone_works_image_perspective` / `_exterior_exone_works_image_plan` と `_exterior_exone_works_on_top` を使用。所在地、旧分類、由来情報など編集対象外の値は保持 |
| 共存テイスト | `exr_works_package`、同じ所属・完了状態・一意の term source key を持つ専用 term / term_taxonomy だけ。名前や slug だけで旧分類を流用しない |
| 新規テイスト | `exterior-exone-renewal:v1:admin:term:works_package:<UUID>` の専用識別。階層なし、slug は自動生成 |
| 分類関連 | 対象の専用事例と専用テイストの関係だけを更新。`exr_works_category` / `exr_works_tag` と旧 taxonomy の関連を保持 |
| 同時操作 | 事例・メタ・分類関連・テイストの最新状態と改ざんできない版情報を保存直前に照合。事例保存とテイスト削除も同じ所有範囲で整合させる |
| 取り込み由来 | 元の key / source hash / fingerprint / parent 情報は由来として固定。現在の編集内容に合わせて元ハッシュを再計算しない |

旧テーマの保存値や共有 options をラベル変更のために書き換えない。新テーマ読込・初回管理画面表示・配布処理だけで投稿や分類を自動生成・変換しない。

## 5. スプリントと検証範囲

S1 は F-01 の一機能として、提案事例とその単一分類を管理する画面、通常ローカルとの整合、対象回帰、独立評価、配布準備を完成させる。既存のお知らせ管理の権限・競合・保存失敗の方式を参考にし、汎用 CMS や全サイト管理基盤へ拡張しない。

検証は外向き通信を止めた隔離環境での CRUD と分類解除、旧データ保護、対象の URL／公開境界を中心にする。特に分類削除で投稿自体を失わないことと、他 taxonomy を巻き込まないことを確認する。通常ローカルの既存管理についても今回変更に関係する保存だけを確認する。全ページ・全環境の再検証は要求しない。

本番の有効テーマは当日の読み取り確認で特定する。前日の旧テーマ有効という状態を前提にしない。新テーマ有効中でも読み込み順と原本ハッシュを確認した対象ファイルだけを配置する。ユーザーの明示指示に従い今回はバックアップを作らず、テーマを切り替えない。ユーザー自身による今後の管理画面操作と、配布時の DB 変更 0 を区別する。
