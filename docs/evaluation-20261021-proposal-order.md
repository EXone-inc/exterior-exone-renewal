# 提案事例の表示順 — Evaluator レビュー

2026-10-21。対象仕様: `spec-20261021-proposal-order.md`。

## 判定

保存・表示・管理 UI と限定 HTML キャッシュ処理の静的レビューでは修正必須の問題なし。実 DB / ブラウザ統合確認と本番反映は親エージェントが担当し、このレビューでは本番への操作は行っていない。

## 確認した点

- 公開アーカイブの通常 `pre_get_posts` と共存 priority 90 の `works-list`、詳細ページ内の `exterior_exone_works_page_cards()` は共通の `menu_order ASC, date DESC, ID DESC` を使用する。TOP の `date DESC` は維持。
- 保存 SQL の変更列は対象投稿の `menu_order` のみ。投稿型・状態・直前順位を WHERE 条件に含め、タイトル・本文・画像・日時・URL・分類へ書き込まない。
- POST、管理者権限、専用 nonce、厳密な ID 配列、重複、対象全件との集合一致、HMAC 版情報を検証する。共存時の所有識別と source key 一意性も既存処理を再利用する。
- 共有 advisory lock と InnoDB transaction で既存提案事例の保存・分類操作と直列化。`FOR UPDATE` 下で対象を再取得し、途中エラー時は rollback。コミット結果が不明な場合も自動再送しない。
- 明示保存時は負順位を使うため、既存初期値 0 の順を配置時に変えず、新規 0 は保存済み事例の後ろに入る。下書きは順位の対象、ゴミ箱は除外する。
- 管理 UI は「すべて」の全件一覧のみ並び替え可能。行内の既存操作 form を別 form で囲まない。ドラッグと上下移動ボタンがあり、保存中・エラー後の再送を抑止し、未保存の離脱を案内する。
- 成功時に管理一覧を再読込することで、`menu_order` を含む既存編集・ゴミ箱操作の版情報も更新する。失敗時は再読込を求め、画面上の順序を確定済みと扱わない。
- 通常ローカルでは `works` 専用の表示順サブメニューに限定し、本番共存では `exr_works` 専用画面に限定する。旧テーマの `works` を混ぜない。
- WP Fastest Cache が存在する場合は、公開 home URL 配下の固定 `/works/(.*)` だけを `specificDeleteCache()` へ一時フィルターで渡す。フィルターは例外時も `finally` で解除し、保存 option・全サイト消去・CDN 呼出しは使わない。該当する desktop / mobile ディレクトリの dev / inode が実行後も残っている場合は、DB 保存済みとキャッシュ失敗を分けて案内する。
